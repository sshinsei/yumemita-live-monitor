1. 按调整说明改调度逻辑

问
按 discovery_scheduler_logic_adjustment.md 修改。
答 · 摘要

核心不是改几个 interval，而是改变决策顺序：

先检查有效 YouTube 预约 ├─ 有 → 围绕 scheduled_start 调度（3h / 近窗 30s） └─ 无 → 再看东京 time band ├─ 非 peak → 2h（no_schedule_off_band） └─ peak → 看 X 日程 ├─ 有 planned_start → 同「已知开播」 └─ 无 → 5min 主动发现

  • x_schedule_monitor/config.py — 新 interval 配置
  • x_schedule_monitor/schedule.py — match_time_band()
  • x_schedule_monitor/monitor.py — 使用 next_run_at、动态 X 刷新
  • config.example.json、相关测试

2. Grace 窗口期如何实现

问
现在的 grace 窗口期是怎么实现的？
答 · 摘要

Grace 不是单独状态机，和 pre-window 一起组成 near window，只影响 discovery 调度。

near_start = start - pre      # 默认 start − 5min
near_end   = start + grace    # 默认 start + 30min
── ordinary 3h ──│──── near_probe 30s ────│── 失效 / 回落 ── │ │ start−5min start+30min ↑ start
  • 在窗内： near_probe，每 30s
  • 窗前： 普通 3h，但 next = min(now+3h, near_start)
  • 过 grace： 当作无有效预约，回落 2h / 5min，不再永久 30s 轮询

选「最近一场有效预约」时也会用 grace：now <= start + grace 才算有效；过期的 upcoming 会被跳过。

Grace 只服务 discovery 间隔，不改采样频率；也不会自动把 streams 标成 ended。

3. 能否知道开播前多久并精确切换频率

问
所以现在的程序可以知道在开播前多久并且精确切换搜索频率吗？
答 · 摘要

有明确预约时：可以。 用 UTC 绝对时间差 start − now，不靠「是否今天」。

阶段条件频率
普通now < start − 5min3h（钳到 near 入口）
近窗start−5min ≤ now ≤ start+30min30s
过期now > start+30min回落无预约逻辑

切换靠每次 discovery 后写 next_run_at，并把普通间隔的下次执行钳到 start−5min，从而对齐升频点。

无预约时： 不知道「开播前多久」，只能按 time band（2h / 5min）提高搜索频率。

局限：只有两档（+ 无预约 2h/5min）；主循环最长约 60s 醒一次；开播时间以 YT/X 为准，改期要等下次刷到新数据。

4. 无预约时 peak 时段频率是否变化

问
无预约时如果落到设定的 peak 时间段搜索频率也会改变对吧？
答 · 摘要

对。 仅在没有有效 YouTube 预约时才看东京 time band。

Band（东京）无预约且无 X
morning 06:00–08:005 分钟
midday 11:45–12:305 分钟
evening_peak 20:00–24:005 分钟
其它时段2 小时

有有效 YT 预约时不会走 peak 的 5 分钟主动发现，一直走预约分支（3h / 近窗 30s）。

5 分钟对应 discovery_active_band_youtube_interval_seconds，不是 time_bands 里旧的 idle_discovery_seconds。

8. 日志里 in 885s 是怎么来的

问
2026-08-02 15:10:14 - INFO - [x_schedule_monitor.monitor]
Next discovery member=nonoka in 885s (interval=10800s)
mode=ordinary reason=youtube_scheduled_outside_near_window
anchor=youtube next_at=2026-08-02T07:25:00Z

这个 885 是怎么来的？
答 · 摘要

885 秒 = 到 near 窗起点的剩余时间，不是 3 小时本身。

  • nonoka 预约 start = 07:30:00Z
  • near_start = start − 5min = 07:25:00Z → 即日志里的 next_at
  • 决策：next_run_at = min(now + 3h, near_start)
  • 当时 now ≈ 07:10:15Z（日志本地 15:10 约 UTC+8）
  • now + 3h 会越过 07:25，故截断到 07:25
  • 07:25:00 − 07:10:15 ≈ 885 秒（约 14 分 45 秒）
字段含义
interval=10800s策略档位：有预约、在 near 外 → 标称 3h
in 885s / next_at真正等到下次 discovery 的时间（已钳到近窗入口）

到 07:25 后再决策，应进入 near_probe（约 30s 一次），直到 start + grace。
